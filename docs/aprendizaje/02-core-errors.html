Paso 2: manejo de errores

Rama feature/core-errors · módulo :core · hecho con TDD

1. El problema que resuelve

Cuando algo falla (se cae el internet, la clave está mal, el cliente ya no existe), el código normalmente lanza una excepción. Si cada pantalla tiene su propio try/catch, pasan cosas malas: unas atrapan todo y esconden errores reales, otras no atrapan nada y la app se cierra, y los mensajes quedan escritos por todas partes con distinto texto.

Tu preferencia fue tener el manejo de errores claro y organizado. La idea es esta, en tres movimientos:

excepción  ──(ErrorMapper)──▶  AppError  ──(ErrorMessageMapper)──▶  texto en español
  (en la capa data)           (tipado)                              (en la capa presentación)

2. Las piezas

ClaseQué hace
AppErrorLa lista cerrada de errores que la app conoce: Network, InvalidCredentials, Validation(campo), NotFound, Conflict y Unknown(causa).
AppResult<T>"Salió bien con un valor" (Success) o "falló con un AppError" (Failure). Los casos de uso devuelven esto en vez de lanzar excepciones.
ErrorMapperEl único lugar donde una excepción se convierte en AppError.
appResultOf(mapper) { ... }Ejecuta un bloque y lo envuelve en AppResult.
ErrorMessageMapperEl único lugar que decide qué texto ve el barbero para cada error.

3. Código clave, explicado

3.1 Una interfaz sellada: sealed interface AppError

sealed interface AppError {
    data object Network : AppError
    data class Validation(val field: ValidationField) : AppError
    data class Unknown(val cause: Throwable? = null) : AppError
    ...
}

Sellada significa que todos los tipos posibles están en este archivo y el compilador los conoce. Cuando haces un when (error), Kotlin te obliga a cubrir todos; si mañana agregas un error nuevo y se te olvida manejarlo, no compila. Es la mejor protección contra "se me olvidó ese caso".

data object es para errores sin datos (Network); data class para los que cargan información (Validation sabe qué campo falló; Unknown guarda la causa para el registro).

Unknown guarda la excepción original pero nunca se muestra al barbero. Se ve "Algo salió mal", y la causa queda disponible para depurar. Hay una prueba que lo verifica.

3.2 AppResult y resolve

inline fun <T, R> AppResult<T>.resolve(transform: (T) -> R): AppResult<R> = when (this) {
    is AppResult.Success -> AppResult.Success(transform(value))
    is AppResult.Failure -> this
}

resolve transforma el valor solo si salió bien; si falló, deja pasar el mismo error sin ejecutar nada. Funciona como el map de las listas, con otro nombre para no confundirlos. Es la única función que tiene AppResult: no construimos una librería entera por si acaso. Para "hacer una cosa si salió bien y otra si falló" basta un when sobre el resultado (ver sección 5).

3.3 Mapeo en un solo lugar

class DefaultErrorMapper : ErrorMapper {
    override fun map(throwable: Throwable): AppError = when (throwable) {
        is IOException -> AppError.Network
        else -> AppError.Unknown(throwable)
    }
}

En Java/Kotlin, SocketTimeoutException y UnknownHostException son subtipos de IOException, por eso con una sola rama cubrimos "sin internet", "se agotó el tiempo" y "no encontró el servidor". Los errores de Firebase se agregan en el Paso 6 envolviendo este mapeador, así :core nunca depende de Firebase.

3.4 appResultOf y la cancelación: el detalle más fino

inline fun <T> appResultOf(mapper: ErrorMapper, block: () -> T): AppResult<T> =
    try {
        AppResult.Success(block())
    } catch (cancellation: CancellationException) {
        throw cancellation          // ← NO se convierte en error
    } catch (throwable: Throwable) {
        AppResult.Failure(mapper.map(throwable))
    }
Las corrutinas (el sistema para trabajo en segundo plano) se cancelan lanzando una CancellationException. Si un catch general la atrapa y la convierte en "error desconocido", la cancelación nunca llega y la pantalla puede quedarse trabajando para nadie. Por eso se vuelve a lanzar. Tiene su propia prueba.

Este es el motivo de fondo de la regla "nada de catch (Exception) suelto": un catch general parece inofensivo y rompe cosas sutiles. Aquí hay un catch, en un lugar, escrito con cuidado.

3.5 Mensajes en un solo lugar

class ErrorMessageMapper {
    fun messageFor(error: AppError): ErrorMessage = ErrorMessage(
        when (error) {
            AppError.Network -> R.string.error_network
            is AppError.Validation -> when (error.field) { ... }
            is AppError.Unknown -> R.string.error_unknown
            ...
        }
    )
}

Devuelve un id de recurso (R.string.error_network), no el texto. La pantalla lo convierte en texto con el contexto de Android. Así este código se prueba en la JVM sin emulador, y los textos viven en core/src/main/res/values/strings.xml, en español, todos juntos.

4. Cómo se hizo: TDD

  1. Tabla de comportamientos (en el chat): tú la aprobaste y quitaste "sesión expirada".
  2. Pruebas primero: escribí 16 pruebas en 4 archivos y las corrí. Resultado: rojo (no compilaba, porque las clases no existían). Ese rojo es la prueba de que las pruebas dependen del código que falta.
  3. Código mínimo para que pasen: verde, 16 de 16.

Cómo se nombran las pruebas

Cada prueba se llama como una frase: given (el punto de partida), when (lo que se hace) y then (lo que debe pasar). Entre comillas invertidas (`...`) Kotlin permite espacios en el nombre, así que el reporte de pruebas se lee solo, sin abrir el código.

MockK en acción

private val mapper = mockk<ErrorMapper>()

@Test
fun `given a block that throws when running appResultOf then should return a failure with the mapped error`() {
    val boom = RuntimeException("boom")
    every { mapper.map(boom) } returns AppError.Conflict   // "cuando te pasen boom, responde Conflict"

    val result = appResultOf(mapper) { throw boom }

    assertEquals(AppResult.Failure(AppError.Conflict), result)
    verify(exactly = 1) { mapper.map(boom) }                // "y confirma que te llamaron una vez"
}

every { ... } returns ... le enseña al falso qué responder; verify comprueba qué se le preguntó. En la prueba de cancelación usamos verify { mapper wasNot Called }: el mapeador nunca debe ser llamado. Preferimos esa forma a verify(exactly = 0) { mapper.map(any()) } porque es explícita y no usa comodines.

5. Cómo se usará más adelante

// En un caso de uso (paso 4 en adelante)
suspend fun createClient(...): AppResult<Client> =
    appResultOf(errorMapper) { dataSource.save(...) }

// En un ViewModel
when (result) {
    is AppResult.Success -> state = state.copy(client = result.value)
    is AppResult.Failure -> effect(ShowMessage(messages.messageFor(result.error)))
}

La pantalla nunca ve una excepción: solo un AppError y un mensaje ya listo.

6. Qué no hicimos a propósito

  • No hay error de sesión expirada (lo quitaste): se agrega cuando exista algo que expire la sesión.
  • No hay mapeo de Firebase todavía: llega en el Paso 6.
  • No hay registro (log) de errores: la causa de Unknown queda guardada, pero dónde se escribe se decide cuando haya algo que registrar.
  • El mapeador no está conectado a Hilt todavía: se conecta cuando el primer ViewModel lo necesite.
