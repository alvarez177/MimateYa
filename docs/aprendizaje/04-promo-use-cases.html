1. Qué hace

En el Paso 3 hicimos el motor (PromoEngine), que calcula pero no guarda nada. En este paso hicimos las dos acciones que usan ese motor y guardan el resultado:

Caso de usoCuándoQué hace
CompleteCutUseCaseEl barbero toca "Completar"Decide cómo se cobra el corte (con el motor), lo guarda una sola vez y devuelve el cobro
RevertCutUseCaseEl barbero toca "Deshacer" o "Revertir"Borra el corte; el saldo vuelve a como estaba

Las reglas salen de la tabla que aprobaste (C1 a C4 y V1 a V3), al final de docs/comportamientos-promos.md.

¿Por qué la interfaz en :core y la implementación en promos? (decisión D4). Completar un corte se dispara desde la agenda, pero las reglas son de promos. Si la agenda dependiera de :feature:promos, los módulos se enredarían. Así, la agenda solo conoce la interfaz de :core, y Hilt (en :app) le entrega la implementación. Por eso también CutCharge se mudó a :core: la agenda necesita leer el cobro para mostrar "Corte gratis".

Regla (decidida por ti): por defecto un caso de uso es una clase concreta, sin interfaz; para probarlo no hace falta, porque MockK simula clases concretas. Solo lleva interfaz cuando lo usa otro feature: CompleteCutUseCase lo usa la agenda, y RevertCutUseCase la agenda ("Deshacer") y la ficha del cliente ("Revertir").

Las implementaciones se llaman CompleteCutDataUseCase y RevertCutDataUseCase (nombres elegidos por ti): conservan la palabra de la interfaz, así se ve de cuál vienen, y siguen terminando en UseCase.

3. Completar: el código, paso a paso

override suspend fun invoke(appointmentId: String, clientId: String): AppResult<CutCharge> {

        return AppResult.Success(existingCut.charge)
    }

    val promoResult = ...    // lee la promo (o falla)
    val historyResult = ...  // lee el historial (o falla)

3.1 El id fijo

CompletedCut.idFor(appointmentId) siempre da el mismo id para el mismo turno: "<turno>-cut". Un turno tiene como máximo un corte. Es la base del "descuento único".

3.2 Por qué revisar primero si ya existe (C2)

Sin esa revisión, el segundo toque recalcularía el cobro con un historial que ya incluye el primer corte. Si el primero fue el gratis, el segundo saldría "pagado" y lo sobrescribiría: el cliente perdería su gratis.

Lo comprobamos con una mutación: quitamos esa línea a propósito y la prueba "given the appointment already has its cut when completing it again ..." falló. Volvimos a ponerla y todo quedó en verde.

Como hablamos, en la agenda (Paso 11) la tarjeta pasa a "completado" al instante y el botón desaparece. Esto es la red de seguridad para lo raro: pantalla recreada, agenda desactualizada o un toque muy rápido.

3.3 El when con return

AppResult solo tiene resolve (decisión tuya del Paso 2). Para encadenar tres lecturas usamos when: si es Failure, return sale de la función devolviendo ese mismo error; si es Success, saca el valor y sigue. Es un poco más largo, pero se lee de arriba a abajo sin trucos. Al final, resolve { charge } convierte el Success(Unit) del guardado en Success(cargo), y si el guardado falló, el fallo pasa intacto.

4. Revertir

override suspend fun invoke(appointmentId: String): AppResult<Unit> {
    val cutId = CompletedCut.idFor(appointmentId)

    return completedCutRepository.deleteCompletedCut(cutId)
}

Es casi solo reenviar la llamada, y está bien: la regla del proyecto dice que siempre hay un caso de uso entre el ViewModel y el repositorio. Lo importante está en el contrato del repositorio: borrar un corte que ya no existe es un éxito (V2). Así, tocar "Deshacer" dos veces no muestra un error. Firestore ya se comporta así al borrar.

Devolver el turno a "programado" en la misma escritura llega en el Paso 11, cuando existan los turnos.

Viven en domain (el "qué"). El "cómo" (Firestore y su DataSource) llega en el Paso 6. getCompletedCuts promete devolver los cortes en el orden en que se completaron, porque la tiquetera depende de ese orden.

6. Corrutinas y despachadores

  • suspend: las funciones pueden esperar (leer o guardar en la nube) sin bloquear la pantalla.
  • kotlinx-coroutines-core 1.11.0 en :core y kotlinx-coroutines-test en las pruebas de promos (para runTest).
  • @IoDispatcher: una etiqueta para pedirle a Hilt "el despachador de red y disco". El código nunca escribe Dispatchers.IO directamente; lo elige DispatchersModule en :app. En pruebas se puede cambiar por uno de prueba. Lo usará el DataSource del Paso 6. Los casos de uso no lo necesitan: solo llaman funciones suspend.
