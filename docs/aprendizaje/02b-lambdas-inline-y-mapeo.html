Lambdas, inline y el mapeo de errores

Documento aparte del Paso 2. Resuelve tres dudas: qué es transform() en resolve, por qué DefaultErrorMapper mapea solo dos casos, y cómo leer appResultOf. Si algo sigue confuso, dime cuál y lo amplío.

Parte 1. Qué es transform: una función que se pasa como valor

1.1 Una función también es un valor

En Kotlin puedes guardar una función en una variable o pasarla a otra función, igual que un número o un texto:

val doblar: (Int) -> Int = { numero -> numero * 2 }

doblar(5)   // 10

El tipo (Int) -> Int se lee: "una función que recibe un Int y devuelve un Int". Lo que está entre llaves { numero -> numero * 2 } se llama lambda: una función sin nombre, escrita en el momento.

1.2 Ya la conoces: map de las listas

val precios = listOf(100, 200, 300)
val conIva  = precios.map { it * 2 }     // [200, 400, 600]

Aquí { it * 2 } es la lambda. map la ejecuta una vez por cada elemento. Dentro de una lambda con un solo parámetro, Kotlin permite llamarlo it en vez de escribir numero ->.

1.3 Ahora, resolve de AppResult

inline fun <T, R> AppResult<T>.resolve(transform: (T) -> R): AppResult<R> = when (this) {
    is AppResult.Success -> AppResult.Success(transform(value))
    is AppResult.Failure -> this
}
Funciona como el map de las listas, pero se llama resolve a propósito: así no se confunde con el map de listas y de Flow, que aparecen en el mismo código.

Léelo por partes:

PiezaSignifica
<T, R>Dos "tipos comodín". T es el tipo del valor que hay dentro del resultado (por ejemplo Int), R es el tipo al que vas a convertirlo (por ejemplo String). Se llaman genéricos: la misma función sirve para cualquier tipo.
AppResult<T>.resolveUna función de extensión: agrega resolve a AppResult sin tocar su código. Por eso la llamas con punto: resultado.resolve { ... }. Dentro, this es ese resultado.
transform: (T) -> RLa lambda que tú le pasas. "Una función que recibe el valor (T) y devuelve otro (R)". transform es solo el nombre del parámetro, como lo sería nombre o edad.
transform(value)Aquí se ejecuta esa función, dándole el valor guardado.
when (this) { ... }Mira si el resultado es éxito o fallo. Como AppResult es sellado, el compilador exige cubrir los dos.
is AppResult.Failure -> thisSi fue un fallo, no hace nada: devuelve el mismo fallo, sin ejecutar transform.

1.4 Seguimiento con valores reales

val resultado: AppResult<Int> = AppResult.Success(2)
val texto = resultado.resolve { "Cortes: $it" }
  1. resultado es Success(2), así que when toma la primera rama.
  2. value vale 2.
  3. Se ejecuta tu lambda con it = 2 y devuelve "Cortes: 2".
  4. El resultado es Success("Cortes: 2"). El tipo pasó de AppResult<Int> a AppResult<String>: eso es T convertido en R.

Y con un fallo:

val fallo: AppResult<Int> = AppResult.Failure(AppError.Network)
val texto = fallo.resolve { "Cortes: $it" }
// texto es el mismo Failure(Network). Tu lambda NUNCA se ejecutó.
Para qué sirve: encadenar pasos sin preguntar "¿falló?" cada vez. Cada resolve solo actúa si todo lo anterior salió bien, y si algo falló, el error viaja intacto hasta el final.

1.5 Un detalle: AppResult<out T>

En la definición dice sealed interface AppResult<out T>. El out significa "T solo sale, nunca entra". Gracias a eso, Failure puede ser AppResult<Nothing> (un fallo no guarda ningún valor) y aun así encajar en AppResult<Int>, AppResult<String>, etc. Por eso is Failure -> this compila sin crear un objeto nuevo.

Parte 2. Qué hace inline

2.1 Sin inline

Cuando pasas una lambda a una función normal, Kotlin crea en memoria un objeto que representa esa lambda y lo entrega. Es un pequeño costo cada vez que la función se llama.

2.2 Con inline

inline le dice al compilador: "no llames a esta función; copia su cuerpo directamente donde se usa". Tú escribes:

val texto = resultado.resolve { "Cortes: $it" }

y el compilador lo convierte, en el código final, en algo equivalente a:

val texto = when (resultado) {
    is AppResult.Success -> AppResult.Success("Cortes: ${resultado.value}")
    is AppResult.Failure -> resultado
}

La lambda desaparece: su contenido queda pegado en medio. No hay objeto ni llamada extra. Tú sigues escribiendo y leyendo la versión corta.

2.3 Entonces, ¿por qué lo usamos aquí?

Seamos honestos: en resolve el ahorro de memoria es pequeño. Las razones reales son otras:

RazónExplicación
Se pueden llamar funciones suspend dentro de la lambdaCon corrutinas esto importa mucho. Como el cuerpo se copia en tu función, una lambda inline puede llamar a Firestore o a cualquier función suspend si la función que la rodea también lo es. Sin inline, la lambda sería otra función y no podría.
Se puede usar return dentroEn una lambda inline, un return sale de tu función, no solo de la lambda. Mira el ejemplo abajo.
Es lo habitualmap, filter, let, forEach de la librería estándar son inline por estas mismas razones.

2.4 Ejemplo del return

fun buscarDos(numeros: List<Int>): String {
    numeros.forEach {                 // forEach es inline
        if (it == 2) return "lo encontré"   // sale de buscarDos, no solo de la lambda
    }
    return "no estaba"
}

buscarDos(listOf(1, 2, 3))   // "lo encontré"

Si forEach no fuera inline, ese return no compilaría.

Cuándo NO usarlo: no se pone inline a todo. En funciones grandes copiaría mucho código en cada sitio y haría la app más pesada. Se usa en funciones pequeñas que reciben lambdas, justo como estas.

Parte 3. appResultOf, línea por línea

inline fun <T> appResultOf(mapper: ErrorMapper, block: () -> T): AppResult<T> =
    try {
        AppResult.Success(block())
    } catch (cancellation: CancellationException) {
        throw cancellation
    } catch (throwable: Throwable) {
        AppResult.Failure(mapper.map(throwable))
    }
LíneaQué pasa
mapper: ErrorMapperQuien sabe convertir una excepción en un AppError.
block: () -> TUna lambda sin parámetros que devuelve algo de tipo T. Es "el trabajo que puede fallar": tú lo escribes.
try { AppResult.Success(block()) }Ejecuta tu trabajo. Si termina sin problema, guarda el valor en un Success.
catch (cancellation: CancellationException) { throw cancellation }Si el trabajo se canceló, lo vuelve a lanzar. No es un error: es el sistema diciendo "ya no hace falta, para". Atraparlo rompería la cancelación.
catch (throwable: Throwable)Cualquier otra cosa que haya salido mal se convierte en Failure(mapper.map(throwable)).
El orden de los catch importa. Kotlin revisa de arriba abajo y usa el primero que encaja. CancellationException va antes que Throwable; si fuera al revés, Throwable (que lo abarca todo) la atraparía primero.

Cómo se usa

// El bloque entre llaves es "block"
val resultado: AppResult<Client> = appResultOf(errorMapper) {
    dataSource.findClient(phone)     // si lanza una excepción, termina como Failure
}

// Se encadena con resolve para transformar el valor sin preguntar si falló:
val nombre: AppResult<String> = resultado.resolve { client -> client.name }

// Y para actuar según el resultado se usa un when:
when (nombre) {
    is AppResult.Success -> println("Hola ${nombre.value}")
    is AppResult.Failure -> println("Error: ${nombre.error}")
}

Como appResultOf es inline, dataSource.findClient(phone) puede ser una función suspend cuando se llama desde otra función suspend. Esa es la razón principal por la que lo hicimos así.

Parte 4. ¿Por qué DefaultErrorMapper solo mapea una regla?

override fun map(throwable: Throwable): AppError = when (throwable) {
    is IOException -> AppError.Network
    else -> AppError.Unknown(throwable)
}

Parece que cubre pocas excepciones, pero hay una trampa a favor: IOException es una "familia". is IOException acepta la clase y todas sus hijas:

Throwable
 └─ Exception
     └─ IOException                      ← aquí atrapamos
         ├─ SocketTimeoutException       (se agotó el tiempo)
         ├─ UnknownHostException         (no encontró el servidor / sin internet)
         ├─ ConnectException             (no pudo conectarse)
         ├─ SSLException                 (problema de conexión segura)
         └─ ... y muchas más

Una sola línea cubre todos los problemas de red. Por eso las tres pruebas de red (IOException, SocketTimeoutException, UnknownHostException) pasan con la misma regla.

¿Y el else?

else -> AppError.Unknown(throwable) es la red de seguridad. Cualquier excepción que no reconozcamos no se esconde ni se pierde: queda como Unknown con la causa guardada. La app no se cierra, al barbero le sale "Algo salió mal" y nosotros tenemos la excepción original para investigar.

¿Por qué no mapear más cosas ya?

Regla de este diseño: solo se mapea lo que sabemos explicarle al usuario. Mapear por adivinar produce mensajes equivocados. Y los demás AppError no salen de este mapeador a propósito:

ErrorQuién lo produceCuándo se agrega
NetworkDefaultErrorMapper (familia IOException)Ya está
UnknownDefaultErrorMapper (todo lo demás)Ya está
InvalidCredentialsMapeador de Firebase (FirebaseAuthInvalidCredentialsException)Paso 6
NotFound, ConflictMapeador de Firebase (según el código del error de Firestore) o la lógica de negocioPaso 6 y siguientes
Validation(campo)La lógica de negocio, que revisa los datos antes de llamar a la red (por ejemplo, correo sin arroba)Paso 7 en adelante
Así el mapeador crece con evidencia: cuando veamos qué excepciones lanza Firebase de verdad, se agregan sus reglas, con su prueba primero. Es el mismo TDD del resto del proyecto.

Una nota sobre el when: se evalúa de arriba abajo y gana la primera rama que encaja. Cuando agreguemos reglas, las más específicas van primero (una subclase antes que su familia).

Para practicar (con respuesta oculta)

1. ¿Qué devuelve esto? AppResult.Success(3).resolve { it + 1 }

Success(4). La lambda recibe 3 y devuelve 4.

2. ¿Y esto? AppResult.Failure(AppError.NotFound).resolve { it + 1 }

Failure(NotFound), el mismo fallo. La lambda no se ejecuta.

3. ¿Qué AppError sale de DefaultErrorMapper().map(IllegalArgumentException("x"))?

Unknown(cause = IllegalArgumentException("x")). No es de la familia IOException, así que cae en el else y conserva la causa.

4. ¿Qué pasa si block lanza CancellationException dentro de appResultOf?

Se vuelve a lanzar tal cual. appResultOf no devuelve nada y el ErrorMapper no se llama.

5. Si quitaras la palabra inline de appResultOf, ¿qué dejaría de poder hacerse?

Llamar a una función suspend dentro del bloque sin que appResultOf misma fuera suspend, y usar return dentro del bloque para salir de la función que la rodea.
