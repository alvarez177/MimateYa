Completar y revertir un corte, paso a paso

Complemento del Paso 4 · CompleteCutDataUseCase y RevertCutDataUseCase en :feature:promos

1. En una frase

ClaseQué hace
CompleteCutDataUseCaseCuando el barbero toca "Completar", decide cómo se cobra ese corte (pagado, gratis por tiquetera o del paquete), lo guarda una sola vez y le dice a la pantalla cómo se cobró.
RevertCutDataUseCaseCuando el barbero toca "Deshacer" o "Revertir", borra el corte de ese turno. Como el saldo se calcula desde los cortes, al borrarlo el saldo vuelve solo a como estaba.

Ninguno de los dos habla con Firebase directamente: le piden las cosas a los repositorios (interfaces). Y ninguno calcula reglas de promos por su cuenta: eso lo hace el PromoEngine del Paso 3.

Pantalla (agenda / ficha)  →  caso de uso  →  repositorios  →  (Firestore, Paso 6)
                                   ↓
                              PromoEngine (reglas)

2. CompleteCutDataUseCase

2.1 Qué recibe y qué devuelve

suspend operator fun invoke(appointmentId: String, clientId: String): AppResult<CutCharge>
  • Recibe: el id del turno que se completa (appointmentId) y el id del cliente (clientId).
  • Devuelve: AppResult.Success(cobro) si salió bien, o AppResult.Failure(error) si algo falló (por ejemplo sin red). El cobro es PAID, FREE_BY_PUNCH_CARD o FROM_PACKAGE; la agenda lo usará para mostrar la animación de "Corte gratis".
  • operator fun invoke permite llamarlo como si fuera una función: completeCut("turno-7", "cliente-3").
  • suspend: puede esperar a la nube sin congelar la pantalla.

2.2 Qué necesita (constructor)

class CompleteCutDataUseCase(
    private val completedCutRepository: CompletedCutRepository,  // historial de cortes
    private val clientPromoRepository: ClientPromoRepository,    // la promo de cada cliente
    private val promoEngine: PromoEngine,                        // las reglas
) : CompleteCutUseCase

2.3 Paso a paso

1

Calcula el id fijo del corte.

val cutId = CompletedCut.idFor(appointmentId)   // "turno-7" → "turno-7-cut"

El mismo turno siempre produce el mismo id. Un turno tiene como máximo un corte.

2

Pregunta si ese turno ya tiene su corte guardado.

val findResult = completedCutRepository.findCompletedCut(cutId)
val existingCut = when (findResult) {
    is AppResult.Failure -> return findResult   // no se pudo preguntar: se devuelve el error
    is AppResult.Success -> findResult.value    // el corte, o null si no existe
}

Primero se guarda la respuesta del repositorio en findResult; luego el when la revisa. Si la consulta falla, return findResult sale de la función en ese mismo instante con el error, y no se cobra nada (regla C4).

3

Si ya existe, termina ahí y devuelve el cobro original (doble toque, regla C2).

if (existingCut != null) {
    return AppResult.Success(existingCut.charge)
}

No vuelve a calcular ni a guardar. Si el primer toque fue un corte gratis, el segundo responde "gratis" también, y el cliente no pierde nada.

4

Lee la promo del cliente.

val promoResult = clientPromoRepository.getPromo(clientId)
val promo = when (promoResult) {
    is AppResult.Failure -> return promoResult
    is AppResult.Success -> promoResult.value   // tiquetera, paquete o null (sin promo)
}
5

Lee el historial de cortes del cliente, en el orden en que se completaron.

val historyResult = completedCutRepository.getCompletedCuts(clientId)
val history = when (historyResult) {
    is AppResult.Failure -> return historyResult
    is AppResult.Success -> historyResult.value
}
6

Le pregunta al motor cómo se cobra este corte y arma el corte completado.

val charge = promoEngine.nextCutCharge(promo, history)
val cut = CompletedCut(id = cutId, charge = charge)

Aquí entran las reglas del Paso 3: si la tiquetera llegó a 10, es gratis; si el paquete tiene cortes, sale del paquete; si no, es pagado (reglas C1 y C3).

7

Lo guarda y devuelve el cobro.

val saveResult = completedCutRepository.saveCompletedCut(clientId, cut)
return saveResult.resolve { charge }

Guardar devuelve Success(Unit) (nada útil) o un fallo. resolve { charge } cambia ese Success(Unit) por Success(cobro); si fue un fallo, lo deja pasar tal cual.

2.4 Tres ejemplos completos

Ejemplo A: Juan tiene una tiquetera de 10 y ya pagó 10 cortes. El barbero completa el turno "turno-7".

  1. id fijo → "turno-7-cut"
  2. ¿existe? → no (null)
  3. sigue
  4. promo → PunchCard(cutsForFreeCut = 10)
  5. historial → 10 cortes PAID
  6. motor → FREE_BY_PUNCH_CARD
  7. guarda CompletedCut("turno-7-cut", FREE_BY_PUNCH_CARD) → devuelve Success(FREE_BY_PUNCH_CARD) → la agenda muestra "Corte gratis"

Ejemplo B: el barbero toca "Completar" dos veces muy rápido en ese mismo turno.

  1. id fijo → "turno-7-cut"
  2. ¿existe? → sí, CompletedCut("turno-7-cut", FREE_BY_PUNCH_CARD)
  3. termina: devuelve Success(FREE_BY_PUNCH_CARD). No lee la promo, no calcula, no guarda.

Si no existiera este paso 3, el motor vería 10 pagados + 1 gratis, diría "pagado", y sobrescribiría el gratis: Juan perdería su corte gratis.

Ejemplo C: no hay red y la lectura de la promo falla.

  1. id fijo → "turno-7-cut"
  2. ¿existe? → no
  3. sigue
  4. promo → Failure(AppError.Network) → termina y devuelve ese error

No se guarda nada ni se inventa un cobro. La pantalla mostrará el mensaje en español de ErrorMessageMapper (Paso 2).

Nota: con Firestore offline (Paso 6) normalmente la lectura sale de la copia local del celular, así que este caso será raro.

3. RevertCutDataUseCase

3.1 Qué recibe y qué devuelve

suspend operator fun invoke(appointmentId: String): AppResult<Unit>
  • Recibe: solo el id del turno. Con eso calcula el id fijo del corte; no necesita el cliente.
  • Devuelve: Success(Unit) ("listo, no hay nada más que contar") o Failure(error).

3.2 Paso a paso

override suspend fun invoke(appointmentId: String): AppResult<Unit> {
    val cutId = CompletedCut.idFor(appointmentId)

    return completedCutRepository.deleteCompletedCut(cutId)
}
1

Calcula el id fijo: "turno-7" → "turno-7-cut". Es el mismo id que usó completar, por eso sabe exactamente qué borrar.

2

Le pide al repositorio borrar ese corte y devuelve lo que el repositorio responda: éxito (regla V1) o el error (regla V3).

3.3 Por qué el saldo vuelve solo

El saldo nunca se guarda: siempre se calcula desde el historial. Si el historial tenía 10 pagados + 1 gratis y se borra el gratis, el motor vuelve a ver 10 pagados y dice "tiene un gratis disponible". No hay que "devolver" nada a mano.

3.4 Dos ejemplos

Ejemplo D: el barbero completó por error el turno de Juan (con Juan aún en la silla) y toca "Deshacer".

  1. id fijo → "turno-7-cut"
  2. borra → Success(Unit). El gratis de Juan vuelve a estar disponible. Cuando termine el corte, lo completa otra vez normalmente.

Ejemplo E: toca "Deshacer" dos veces. La segunda vez el corte ya no existe; borrar algo que no existe es un éxito (lo promete el repositorio, regla V2). Devuelve Success(Unit) y la pantalla no muestra ningún error.

Lo que todavía no hace: devolver el turno a "programado" en la misma escritura. Eso llega en el Paso 11, cuando existan los turnos.

5. Sobre los nombres

Hoy cada uno tiene dos piezas: la interfaz en :core (CompleteCutUseCase, RevertCutUseCase), que es lo que verán la agenda y la ficha del cliente, y la implementación en :feature:promos, que es todo lo explicado arriba. Como la interfaz ya usa el nombre corto, la implementación necesita otro. Elegiste CompleteCutDataUseCase y RevertCutDataUseCase: conservan la palabra de la interfaz y terminan en UseCase.
