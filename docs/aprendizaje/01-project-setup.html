Paso 1: base del proyecto

Rama feature/project-setup · MimateYa v1 · Explicación para aprender, no para entregar

1. Qué quedó funcionando

  • La app ya no es un solo módulo: ahora hay 5 módulos (:app, :core y tres features).
  • Hilt (inyección de dependencias) está conectado y compila con AGP 9.4.1.
  • Hay tres ambientes instalables a la vez: dev, QA y prod, cada uno con su nombre y su icono (DEV ámbar, QA violeta, PROD azul).
  • MockK y kotlinx-collections-immutable ya están en el proyecto, listos para el paso 2.

2. Los módulos y por qué existen

settings.gradle.kts
include(":app")
include(":core")
include(":feature:agenda")
include(":feature:clients")
include(":feature:promos")

Un módulo es una carpeta con su propio build.gradle.kts. Separar el código así tiene dos ventajas que nos importan:

  • El compilador hace cumplir las reglas. :feature:agenda depende de :core pero no de :feature:promos. Si por error alguien importa una clase de promos en agenda, simplemente no compila.
  • Compilación más rápida. Gradle solo recompila los módulos que cambiaron.
MóduloPara quéDepende de
:appPunto de entrada, navegación y cableado de Hilttodos
:coreErrores, modelos compartidos, interfaces de repositorio—
:feature:agendaTurnos:core
:feature:clientsClientes:core
:feature:promosPlanes y motor de promos:core
Dentro de cada feature, el código irá en paquetes domain, data y presentation (decisión tuya). Todavía no hay paquetes porque no hay código: no creamos carpetas vacías.

3. El catálogo de versiones

gradle/libs.versions.toml
[versions]
hilt = "2.60.1"

collectionsImmutable = "0.5.2"

[libraries]
hilt-android = { group = "com.google.dagger", name = "hilt-android", version.ref = "hilt" }

Todas las versiones viven en un solo archivo. En los build.gradle.kts se usan como libs.hilt.android: cambiar una versión es tocar una línea, no cinco archivos.

Actualizamos core-ktx, lifecycle y activity-compose (estaban muy atrasadas) y las consultamos en el repositorio de Maven antes de escribirlas, para no inventar versiones.

4. Hilt: qué es y qué hicimos

@HiltAndroidApp
class MimateYaApplication : Application()

@AndroidEntryPoint
class MainActivity : ComponentActivity() { ... }

Inyección de dependencias significa que una clase no crea lo que necesita: lo recibe. Por ejemplo, un ViewModel recibirá su repositorio en el constructor. Eso hace el código fácil de probar con MockK, porque en la prueba le pasas un falso.

  • @HiltAndroidApp en la clase Application es la raíz del grafo de dependencias.
  • @AndroidEntryPoint en la actividad permite que reciba inyección.
  • El manifest apunta a la nueva clase: android:name=".MimateYaApplication".
Riesgo que verificamos primero: AGP 9 trae Kotlin integrado, y no sabíamos si KSP (el procesador que genera código de Hilt) funcionaba así. Compiló sin cambios: corrieron kspDevDebugKotlin y las tareas hilt*.

5. Los tres ambientes

app/build.gradle.kts
flavorDimensions += "environment"
productFlavors {
    create("dev")  { applicationIdSuffix = ".dev"; resValue("string", "app_name", "MimateYa Dev") }
    create("qa")   { applicationIdSuffix = ".qa";  resValue("string", "app_name", "MimateYa QA") }
    create("prod") {                                resValue("string", "app_name", "MimateYa") }
}

Un product flavor es una variante de la misma app con su propia configuración. Aquí hay tres, y cada una tiene un applicationId distinto:

AmbienteapplicationIdNombre en el celular
devcom.salvarez.mimateyaandroid.devMimateYa Dev
qacom.salvarez.mimateyaandroid.qaMimateYa QA
prodcom.salvarez.mimateyaandroidMimateYa

Como los ids son distintos, Android las trata como apps diferentes: puedes tener las tres instaladas a la vez sin que se pisen. En el Paso 6, cada una usará su propio proyecto de Firebase, así los datos de prueba nunca se mezclan con los reales.

Detalle que apareció: AGP 9 pide activar buildFeatures { resValues = true } para usar resValue(...). Sin eso la configuración falla con "custom resource values, but the feature is disabled". También quitamos app_name de strings.xml, porque ahora lo define cada ambiente (si estuviera en los dos sitios habría un duplicado).

Un icono distinto por ambiente

AmbienteFondoLetras
devÁmbar #F59E0BDEV
qaVioleta #7C3AEDQA
prodAzul de la marca #1D4ED8PROD

El icono de Android moderno es adaptativo: dos capas (fondo y primer plano) que el sistema recorta con la forma que elija el celular (círculo, cuadrado redondeado...). Cada ambiente tiene sus dos capas en su propia carpeta:

app/src/dev/res/drawable/ic_launcher_background.xml   (color de fondo)
app/src/dev/res/drawable/ic_launcher_foreground.xml   (letras "DEV")
app/src/qa/res/drawable/...
app/src/prod/res/drawable/...

Los source sets por flavor funcionan así: cuando compilas devDebug, Gradle junta src/main con src/dev, y lo que está en dev gana. Por eso borramos los dibujos de main (el robot de la plantilla): cada ambiente trae los suyos. El archivo mipmap-anydpi/ic_launcher.xml no cambia: sigue apuntando a @drawable/ic_launcher_background y _foreground, y Android resuelve cuál usar según el ambiente.

Las letras están dibujadas con trazos (strokeColor, strokeLineCap="round") en vez de usar una fuente, porque un vector no puede llevar texto. Quedan dentro de la zona segura (x e y entre 21 y 87 de 108) para que el sistema no las corte.

Para el icono real: el de prod hoy dice "PROD" porque así lo pediste para distinguirlo. Cuando exista la marca definitiva (Paso 5 o antes de publicar), el de prod pasa a ser el logo sin letras, y dev y QA conservan sus etiquetas.

6. Pruebas y comandos

# compilar un ambiente
./gradlew assembleDevDebug

# pruebas unitarias
./gradlew testDebugUnitTest testDevDebugUnitTest

Los módulos de librería no tienen variantes, así que usan testDebugUnitTest. :app sí las tiene, por eso su tarea se llama testDevDebugUnitTest. Todos los módulos ya incluyen JUnit y MockK.

7. Recomposición: por qué collections-immutable

Compose omite recomponer una función si sus parámetros no cambiaron. Una List normal de Kotlin puede ser mutable por detrás, así que Compose no está seguro de que no cambió. ImmutableList le da esa garantía. Lo usaremos en los UiState de las pantallas. Está en :core como api(...), para que los features lo reciban sin declararlo otra vez.

8. Cómo probarlo tú

  1. En Android Studio, abre Build Variants y elige devDebug, qaDebug o prodDebug.
  2. Ejecuta la app: todavía muestra el "Hello Android" de la plantilla; la pantalla real llega en pasos posteriores.
  3. Instala dos variantes en el mismo celular y comprueba que aparecen con nombres distintos.
